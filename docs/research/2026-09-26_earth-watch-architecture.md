# Static files outlive servers: Earth Watch's ten-year architecture

The future-proof shape for Earth Watch is "the repository is the platform, static open-format files are the product, and the LLM is a step inside a deterministic state machine, never the thing that decides." Concretely: the ledger should be an event-sourced log of canonical-JSON finding events wrapped as in-toto/DSSE statements, committed to a C2SP `tlog-tiles` Merkle log with Ed25519-signed checkpoints and anchored externally in Sigstore Rekor v2 and OpenTimestamps, mirrored as append-only GeoParquet for analytics; the watch agent should be a TypeScript "Watch Kernel" that owns sweeps, rules, a step journal, the review queue and provenance, calling earthdeck's 26 tools in-process and invoking any LLM only through a narrow `LlmStep` adapter; attribution and publication should copy the two-clock, confidence-tiered, four-eyes, right-of-reply, "name assets not people" rules that UNEP MARS, GFW, Carbon Mapper, Climate TRACE, Global Fishing Watch and the Berkeley Protocol have converged on; the world pulse should be built on OWID, World Bank, UN, UNHCR and UCDP zero-key CC-BY APIs with every series snapshotted locally; and the public site should be the existing Vite/MapLibre build served statically with PMTiles, GeoParquet and DuckDB-WASM, while the Node `http` dashboard stays a local mission-control surface. This is where the entire transparency-log ecosystem (Certificate Transparency, Go sumdb, Sigstore, Debian), the cloud-native geospatial ecosystem (GeoParquet 2.0 on native Parquet types, STAC 1.1 as an OGC standard, PMTiles, EOPF Zarr) and the agent-reliability literature (Geo-OLM's 100× cost cut from state-machine prompting, the "fail-plausible" silent-failure taxonomy) all landed in 2025–2026, and it costs $0–5/month to run. The prior plan's core instincts (JSONL ledger, Actions cron, static export, deterministic layer decides, humans name parties) are right; its specific mechanisms need four changes: a plain `prevHash` chain is not independently verifiable and must become a witnessed Merkle log; "every N hours" Actions cron must become watermark-driven catch-up with a keepalive and a watchdog because GitHub schedules were hours late or skipped outright in 2026; the ledger must be event-sourced rather than mutable status rows; and GitHub Pages must not be the data CDN. The main durability threat is not technology but US federal data (NOAA decommissions, S-NPP ending 1 Nov 2026, NSIDC on "basic" service), so every upstream needs a configured substitute and a local snapshot. Everything the research could not confirm against a live endpoint is flagged "verify live" below.

## Witnessed Merkle logs, not hash chains, make findings independently verifiable

The prior plan's ledger (`prevHash → hash` over canonical JSON in a JSONL file) is tamper-evident only against a naive editor; the operator who controls the file can rewrite history and re-chain it, and a reader has nothing external to compare against. The transparency ecosystem solved this a decade ago and in 2024–2026 converged on a design that needs no server at all. The C2SP `tlog-tiles` spec serves an RFC 6962 Merkle tree as static "tiles" ("concatenated sequences of consecutive Merkle Tree Hashes at a certain tree height") so that "clients can fetch all the tiles they need in parallel and compute any desired proof" ([C2SP tlog-tiles](https://c2sp.org/tlog-tiles@v0.1.0)); tiles are 256 hashes wide, endpoints are `<prefix>/checkpoint`, `<prefix>/tile/<L>/<N>` and `<prefix>/tile/entries/<N>`, and the design explicitly prioritises "static resources which can be fetched with HTTP GET requests, and which can be efficiently cached and compressed" ([C2SP tlog-tiles.md](https://github.com/C2SP/C2SP/blob/main/tlog-tiles.md)). The checkpoint is a signed note (origin line, tree size, base64 root hash, then `— keyname signature` lines) under the rule that "a log MUST not sign any checkpoint which is inconsistent with any checkpoint it previously signed" and that "clients MUST ignore unknown signatures", which is what enables key rotation and witness cosigning ([C2SP tlog-checkpoint.md](https://github.com/C2SP/C2SP/blob/main/tlog-checkpoint.md)). This is not a niche choice: Certificate Transparency has moved to it ("what started as the Sunlight API is now the Static CT API"), Let's Encrypt shut down its RFC 6962 logs on 28 Feb 2026 ([sunlight.dev](https://sunlight.dev/)), Google's Trillian v1 is "in maintenance mode" in favour of the tiled Tessera ([google/trillian](https://github.com/google/trillian)), and Sigstore's Rekor v2 (GA Oct 2025) is "fully CDN-cacheable for reads, and sharded by year" on Tessera ([sigstore/rekor-tiles](https://github.com/sigstore/rekor-tiles)). The cautionary counter-example is AWS QLDB, whose managed hash-chained ledger shut down on 31 July 2025 with a recommended migration path that "loses cryptographic verifiability" ([InfoQ](https://www.infoq.com/news/2024/07/aws-kill-qldb/); [DoltHub](https://www.dolthub.com/blog/2024-08-12-qldb-deprecated-alternatives/)).

What makes the log verifiable *against the operator* is external witnessing, and for a zero-budget project it is free. Every checkpoint should be (a) signed keylessly from GitHub Actions via `@sigstore/sign`, where Fulcio "mints a new short-lived X.509 certificate binding the public key to the workflow's OIDC identity" and, for public repos, the bundle "is also written to an immutable transparency log that is publicly readable" ([GitHub Docs: Artifact attestations](https://docs.github.com/en/actions/concepts/security/artifact-attestations)); (b) stamped with OpenTimestamps, whose donation-funded public calendars aggregate commitments into Bitcoin transactions and produce standalone `.ots` proofs ([opentimestamps.org](https://opentimestamps.org/)); and optionally (c) stamped by Sigstore's open-source RFC 3161 timestamp authority ([sigstore/timestamp-authority](https://github.com/sigstore/timestamp-authority)). Git history and every clone become weak witnesses (the owner can force-push), while Rekor and Bitcoin are strong ones; a verifier records the last checkpoint it saw and demands a consistency proof from tiles, so any split view is detectable after the fact ([Confium: Transparency logs](https://www.confium.org/concepts/transparency-logs/)). Sigsum's design shows why witnesses cost nothing to run: "the log provides the O(log N) consistency proof when requesting a cosignature, and the witness only needs to store the O(1) latest checkpoint" ([Sigsum design](https://git.sigsum.org/sigsum/plain/doc/design.md)). Joining the Armored Witness / transparency.dev network for cosigned checkpoints is the v3 aspiration; whether it accepts small arbitrary logs is unconfirmed (verify live). A blockchain is the wrong tool: it buys ordering without a trusted sequencer, but Earth Watch *has* a natural sequencer (the project) and needs auditability *of* that sequencer, which witnessed Merkle logs give directly and which Bitcoin supplies as a free anchor through OpenTimestamps.

The data model must be event-sourced, because mutable status rows cannot live in an append-only log. Each log entry is a DSSE envelope whose payload is the RFC 8785 JCS canonicalisation of an in-toto Statement ("a fixed, lightweight 'Statement'" with subject digests and a typed predicate) ([in-toto/attestation](https://github.com/in-toto/attestation); [RFC 8785](https://www.rfc-editor.org/info/rfc8785/)); the predicate type is a project-owned URL such as `https://earthdeck.dev/finding-event/v1` and the event kinds are `created`, `evidence_added`, `status_changed`, `retracted`. A finding is a projection (fold) over events sharing a `findingId`; the current-state table is a rebuildable materialised view, never authoritative. Identifiers are UUIDv7 (RFC 9562, 48-bit millisecond timestamp, now native in PostgreSQL 18 and Python 3.14), timestamps are RFC 3339 `Z`, geometry is GeoJSON RFC 7946, and evidence references are STAC Items, now an OGC Community Standard (Oct 2025) aligned with OGC API – Records (approved Apr 2025) ([RFC 9562](https://www.rfc-editor.org/info/rfc9562/); [OGC 25-004](https://docs.ogc.org/cs/25-004/25-004.html); [OGC announcement](https://www.ogc.org/announcement/ogc-membership-approves-ogc-api-records-part-1-core-as-an-official-ogc-standard/)). Choosing IETF RFCs and OGC standards for every field is the strongest ten-year signal available. The predicate should carry, per the Berkeley Protocol's demands for chain of custody and documented methodology ([OHCHR Berkeley Protocol](https://www.ohchr.org/sites/default/files/2024-01/OHCHR_BerkeleyProtocol.pdf)): scene IDs and acquisition times, `method{name, version, codeDigest, params}`, the hash of each derived raster or render, the reviewer identity for human actions, an intra-finding `prev` hash for cheap fork detection, and a free-text "alternative explanations considered" field. PROV-O semantics (Entity/Activity/Agent, `wasGeneratedBy`/`used`) are expressed as plain JSON keys, mappable to RDF if ever wanted; W3C Verifiable Credentials 2.0 is a Recommendation since May 2025 but drags in JSON-LD contexts without adding verifiability beyond DSSE + Rekor, so it is at most an export format ([W3C news](https://www.w3.org/news/2025/the-verifiable-credentials-2-0-family-of-specifications-is-now-a-w3c-recommendation/)). Publish the JSON Schema (2020-12) as the language-neutral contract and keep zod as the runtime validator; never break v1, add v2 predicate types alongside.

The Node dependency plan matches earthdeck's pinned, few-deps discipline. Sigstore signing and verification come from the official `@sigstore/sign` (5.0.0, mid-2026) and `@sigstore/verify` packages, Apache-2.0 and used by the npm CLI itself, and they already support "DSSE bundles with Rekor v2 hashedrekord entries" ([sigstore-js](https://github.com/sigstore/sigstore-js); [@sigstore/sign](https://www.npmjs.com/package/@sigstore/sign)). JCS comes from `canonicalize` (erdtman, "verified to be compatible with JCS according to RFC 8785 itself") or is vendored as ~100 lines, with the RFC 8785 test vectors run in the offline suite so a Node upgrade cannot silently change number serialisation ([canonicalize](https://github.com/erdtman/canonicalize)). No maintained JavaScript `tlog-tiles` library was found, and the Ethereum-oriented Merkle packages use sorted-pair hashing that is not RFC 6962 and would make the log unverifiable by standard Go/Rust tooling ([@openzeppelin/merkle-tree](https://www.npmjs.com/package/@openzeppelin/merkle-tree)); the RFC 6962 hashing (`H(0x00‖leaf)`, `H(0x01‖L‖R)`), tile writer/reader, signed-note handling and proof computation are ~150 lines over `node:crypto` (Node ≥20 has stable Ed25519 and SHA-256), tested against the C2SP examples and Go's `sumdb/tlog` vectors. That the log core never depends on npm at all is itself a durability win.

For analytics, mirror the same events into append-only GeoParquet partitioned `year=/month=` on object storage and query it with DuckDB. GeoParquet's current release is 2.0.0, "based on Parquet Geospatial Logical Types" so the geometry type now lives in the Parquet format itself (OGC approval pending) ([opengeospatial/geoparquet](https://github.com/opengeospatial/geoparquet/blob/main/README.md)); DuckDB reads and writes GeoParquet natively since v1.1 with the spatial extension ([duckdb discussion #14274](https://github.com/duckdb/duckdb/discussions/14274)); and Overture Maps publishes its planet-scale dataset exactly this way with DuckDB as the documented access path ([Overture docs](https://docs.overturemaps.org/getting-data/duckdb/)). Write 1.1 WKB today (every reader accepts it) and flip to 2.0 native geometry when the DuckDB Node path supports it (verify live: `@duckdb/node-api` extension loading). Per-AOI time series go in a "long" table `(aoi_id, ts, variable, value, source, quality)`; evidence chips are COG for analysis-grade rasters and PNG/WebP for pure visual evidence, each with a STAC 1.1 Item written into a static stac-geoparquet file so the catalog itself is a Parquet file rather than an API ([stac-geoparquet-spec](https://github.com/radiantearth/stac-geoparquet-spec/blob/main/stac-geoparquet-spec.md)); AlphaEarth embeddings are fixed-length float-list columns beside the finding row, with DuckDB brute-force cosine similarity until the active partition outgrows interactive latency. Do not start with PostGIS: it forces a 24/7 server and backups a zero-budget team cannot fund, and it is justified only in v3 for a live API needing sub-100 ms point queries, populated from the Parquet ledger and never the source of truth. Zarr v3 + Icechunk 1.0 (transactional, git-like versioning, stable since July 2025) is the right answer only when dense per-AOI raster history is retained, in v2 ([Icechunk](https://icechunk.io/en/stable/overview/)).

## A deterministic kernel runs the sweep; the LLM is one journaled step

The 2025–2026 consensus on autonomous agents, from both the EO research line and the durable-execution industry, is "deterministic workflow engine on the outside, LLM as a step on the inside." Geo-OLM modelled EO workflows as finite state machines that "decouple task progression from tool calling" and reached results "within 10% of GPT-4o, while reducing inference costs by two orders of magnitude from $500–$1000 to under $10" ([arXiv 2504.04319](https://arxiv.org/abs/2504.04319)); the April 2026 "Agentic AI for Remote Sensing" paper argues EO agents need "structured geospatial state, tool-aware reasoning, verifier-guided execution" and "trajectory-level evaluation beyond final-answer accuracy" ([arXiv 2604.24919](https://arxiv.org/abs/2604.24919)); and the UnivEARTH benchmark found generic LLM agents at 33% accuracy "partly due to code execution failures over 58% of the time" ([arXiv 2504.12110](https://arxiv.org/abs/2504.12110)). The most important production warning comes from a longitudinal study of a ~40-job agent runtime across eight providers, which recorded 22 incidents in eight weeks, found the meta-pattern "a failure whose error signal never reaches a human in actionable form" at least 28 times, and named "fail-plausible" as the dominant class: "the LLM actively transforms the error into fluent, plausible narrative content delivered to the user" ([arXiv 2606.14589](https://arxiv.org/abs/2606.14589)). The design consequence is that the Watch Kernel, not the model, must own the sweep loop, the finding schema, the thresholds and the publication gate.

The kernel is a pure-TypeScript package (`packages/watch/`) with no LLM dependency in its core. `sweep.ts` iterates AOIs × detectors and calls the same client functions the MCP tools wrap, in-process (as `demo.ts` already does), with every call journaled. `rules/` holds versioned detector predicates (`burn_scar@1.2`, `flood@1.0`, `fire_cluster@1.0`, `methane_anomaly@1.0`) that each declare their required confirming signal(s) and a `min_confirmations`. A candidate becomes a finding only when the primary detector crosses a pre-registered threshold *and* at least one independent signal agrees, where independent means a different sensor physics (Sentinel-1 SAR vs Sentinel-2 optical), a different provider (FIRMS fire vs NBR burn index; EONET event vs local NDVI drop) or a later revisit. This mirrors operational EO practice: GLAD alerts start "unconfirmed" and become "confirmed" only if "loss is also flagged in one of the next four Landsat images" ([GLAD alerts explained](https://globalnaturewatch.org/blog/data-and-tools/glad-deforestation-alerts/)), and GFW's integrated alerts reach highest confidence "only … when multiple alerts systems detect a disturbance in the same pixel location" because "it's uncommon for two systems to commit the same error since they use different data streams and algorithms" ([GFW integrated alerts](https://www.globalforestwatch.org/blog/data-and-tools/integrated-deforestation-alerts/)). SAR alone is "known for having an excess number of false positive detections" and industry practice is that optical "brings context and confirmation to detections made by SAR" ([Windward](https://windward.ai/blog/electro-optical-eo-imagery-in-maritime-intelligence/)). Confirmation is implemented in the deterministic layer, never by an LLM judge: judge models show position bias across ~150,000 evaluation instances, roughly 66% agreement with humans on some tasks, and "preference leakage" when generator and judge share a family ([Adaline: LLM-as-judge reliability](https://www.adaline.ai/blog/llm-as-a-judge-reliability-bias)).

The journal is the durability layer. In v1 it is SQLite (or, given Node ≥20 without `node:sqlite`, the same GeoParquet/JSONL files plus an in-memory index) with tables `sweeps`, `steps` (name, input_hash, output_ref, status, attempts), `tool_calls` (tool, args, response_sha256, blob path, provider scene/record ids), `candidates`, `findings` (UNIQUE `finding_key`), `narrations` (model id, prompt hash, transcript hash, schema hash, usage/cost), `reviews`, `publications` and `heartbeats`. Step memoisation on `input_hash` gives "80% of durable execution with zero cluster dependency", the argument of the widely shared "durable execution for AI agents in 150 lines" post ([HackerNoon](https://hackernoon.com/you-dont-need-temporal-yet-durable-execution-for-ai-agents-in-150-lines)); LangChain's own rule of thumb is to add Temporal "once a workflow makes 3 or more external/tool calls, pauses for hours or days, or performs actions where duplicate retries would be harmful" ([LangChain: LangGraph vs Temporal](https://www.langchain.com/resources/langgraph-vs-temporal)). Exactly-once *publication* is achieved by idempotency keys the kernel owns: `finding_key = sha256(rule_id, aoi_id, sensor_pass_id | date_bucket)` inserted under a UNIQUE constraint before any narration is requested, and the publish step checking `published_at IS NULL` in the same transaction; LLM steps are at-least-once and made pure (input hash → stored output). Temporal activities carry the same requirement: "Activity idempotency is a production requirement, not an optimization" ([Jacar](https://jacar.es/en/durable-agent-execution-with-temporal/)). Avoid LangGraph.js as the system of record: its per-node checkpointer writes are async by default "risking data loss unless set to sync" and it has open resume bugs with Anthropic tool ids ([Medium comparison](https://medium.com/data-science-collective/inngest-vs-temporal-vs-dbos-vs-langgraph-7d0557ff6c53); [langgraphjs #1423](https://github.com/langchain-ai/langgraphjs/issues/1423)).

The LLM enters through one interface, `LlmStep.run(input, schema, tools) → {json, transcript, usage, model_id}`, with Claude Code headless as the first adapter and the Anthropic SDK, OpenAI Agents SDK, Vercel AI SDK and Ollama as alternates. Claude Code headless already gives `--json-schema` structured output (hard error on invalid schema since v2.1.205), `--mcp-config`, `--bare` (skips hooks and CLAUDE.md discovery; "recommended mode for scripted and SDK calls"), `--permission-prompts none` for unattended runs, `total_cost_usd` per run, a `system/init` event whose `mcp_server_errors` array lets a CI gate fail fast, and `.jsonl` transcripts that can be replayed with `--resume` ([code.claude.com headless](https://code.claude.com/docs/en/headless)); `PreToolUse` hooks with exit 2 give deterministic deny lists outside the model ([hooks guide](https://code.claude.com/docs/en/hooks-guide)). Note that since 15 June 2026 headless SDK usage "draws from a separate weekly token pool on Claude Pro and Max plans" ([Totalum](https://www.totalum.app/blog/claude-agent-sdk-totalum-2026)), and that the kernel must post-validate every model output with Ajv regardless of provider guarantees and retry once with the error. Every LLM output schema carries a mandatory `evidence_refs[]` that must resolve to `tool_calls` ids, and a `verify/` module rejects narrations whose numbers do not match tool outputs within tolerance or that make banned claims (causation, named parties) for the finding's tier. Tool errors are surfaced to the workflow as typed failures, never fed to the model as text it can explain away. Cost then scales with confirmed findings, not monitored area: detectors run with no LLM; a small model (Haiku-class or a local open model via Ollama) only ranks and deduplicates candidates that pass thresholds; a frontier model narrates only confirmed findings. Prompt caching makes the stable prefix cheap: cache reads cost 0.1× base input (0.025× on Claude Fable 5.1), the invalidation hierarchy is `tools → system → messages` so the 26 stable tool schemas belong at the top and must never change mid-day, and the minimum cacheable prefix is 512–4,096 tokens depending on model ([platform.claude.com prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)).

The MCP protocol itself rewards this shape. The 2026-07-28 spec removed the `initialize` handshake and `Mcp-Session-Id` so servers "can run behind a plain round-robin load balancer", documented W3C Trace Context (`traceparent`, `tracestate`, `baggage`) in `_meta`, added `ttlMs` and `cacheScope` on list responses, accepted full JSON Schema 2020-12 for tool schemas, graduated Tasks to an extension, and deprecated Roots, Sampling and Logging with a 12-month removal window (Sampling "replaced by direct integration with LLM provider APIs", Logging by stderr/OpenTelemetry) ([MCP blog: 2026-07-28 release candidate](https://blog.modelcontextprotocol.io/posts/2026-07-28-release-candidate/)). For earthdeck this means: stay stateless, pass `traceparent` through `_meta` so the sweep's OTel trace id flows into every tool call, declare a typed `outputSchema` and `structuredContent` on all 26 tools so the kernel can validate them, never design the server to ask the host model for completions, and mark all existing tools `readOnlyHint: true, idempotentHint: true, openWorldHint: true` while any future `publish_finding` tool is `destructiveHint: true` and, in Claude Code, `requiresUserInteraction` so no permission mode can auto-run it (Claude Code cancels unanswered elicitations under `--permission-prompts none` unless a hook answers) ([code.claude.com headless](https://code.claude.com/docs/en/headless)). Emit OTel spans today using the GenAI attribute names (`invoke_agent`, `execute_tool`, `chat`, `gen_ai.*`) but pin your own schema version: as of mid-July 2026 "every single gen_ai.* attribute, span, metric, and event … carries the stability badge 'Development'" and the conventions were moved to a separate repo with no tagged release ([John Hodge](https://john-hodge.com/blog/opentelemetry-genai-semantic-conventions/)).

The scheduler is the weakest link in the prior plan. GitHub Actions `schedule` runs on best-effort infrastructure; 2026 reports include a daily job "firing 14.5 hours late on the 6th, 12.5 hours late on the 7th, and not running at all on the 8th", and the community warning that "under heavy enough load, a scheduled run can be skipped entirely — no run, no error, no notification" ([GitHub community #207346](https://github.com/orgs/community/discussions/207346)). Scheduled workflows in public repos are also auto-disabled after 60 days without a push, and when that happens "all triggers in that workflow file are disabled" ([SteadyCron](https://steadycron.com/guides/github-actions-schedule-not-running/); [GitHub community #32197](https://github.com/orgs/community/discussions/32197)). The v1 mitigations are cheap and mandatory: every run computes `since = last_watermark(aoi, source)` from the ledger rather than "now − interval" so late and missed runs self-heal; results are keyed by `(aoi_id, source, observation_time)` so re-runs are upserts; the schedule lives in a dedicated workflow with `workflow_dispatch`, an off-round minute, a `concurrency` group and the keepalive action that "generates a commit if no authorship activity for 41 days" ([gh-action-keepalive](https://github.com/efrecon/gh-action-keepalive)); every sweep writes a heartbeat; and a separate cheap watchdog (an external cron ping, a second workflow on a different minute, or Cloudflare Workers Cron, whose triggers are free with 1-minute granularity but a 10 ms CPU budget, so dispatch only) alerts when `now − last_completed_sweep > 2× period` ([Cloudflare Workers pricing](https://developers.cloudflare.com/workers/platform/pricing/)). Public repos get unlimited standard-runner minutes, and matrix jobs sharded by geohash give hundreds to thousands of AOIs per hour ([GitHub Actions billing](https://docs.github.com/billing/managing-billing-for-github-actions/about-billing-for-github-actions)). Because Sentinel revisit is 5 days, GFW alerts are daily-to-weekly and FIRMS latency is ~3 hours, "roughly hourly, ±30 min" is adequate for every source. Budgets and circuit breakers complete the ops layer: per-sweep caps on tool calls, tokens/USD and wall-clock; a daily budget with graduated ALERT → THROTTLE (narrate top-N only) → CIRCUIT_BREAK (detectors only, page a human) states, following the SRE-for-agents pattern ([Microsoft: SRE for autonomous agents](https://techcommunity.microsoft.com/blog/linuxandopensourceblog/applying-site-reliability-engineering-to-autonomous-ai-agents/4521357)); loop detection aborting a step when the same (tool, args) repeats more than twice; and data-API 429s mapped to a typed "coverage gap" result with the watermark unchanged.

## Precedents converge on two clocks, tiered confidence and naming assets not people

The trust and publication policy should not be invented; the systems Earth Watch most resembles have run for three to ten years and their rules are legible. UNEP's Methane Alert and Response System is the closest analogue to detect → verify → attribute → route → track, and its numbers set expectations: "Government and industry responses to UNEP's more than 3,500 satellite methane alerts climbed from one to 12 percent in the past year", with 25 documented mitigation cases in ten countries since 2022, while "some countries achieving 100 percent response rates" and others near zero ([UNEP press release](https://www.unep.org/news-and-stories/press-release/better-data-driving-action-methane-emissions-more-work-needed)). A UN body with diplomatic access gets ~12%; a volunteer OSS ledger should design "no response after N days" as a first-class, publicly displayed state rather than a failure, and should route to actors with a legal duty, since the EU Methane Regulation now obliges the Commission to run a MARS-based monitoring tool and a rapid-reaction mechanism that requests "details on the remedial measures taken or planned" ([Clifford Chance](https://www.cliffordchance.com/content/dam/cliffordchance/briefings/2025/01/2025-EU-Methane-Regulation.pdf)). MARS's timing rule is the de facto right-of-reply standard: "Data is posted on Eye on Methane 30 days after detection. If a notification was issued and feedback on the plume notification was received from either the operator or the government, the data is posted 30 days after the date of notification", and the feedback is published alongside the plume ([UNEP MARS FAQ](https://www.unep.org/topics/energy/methane/mars-frequently-asked-questions-faq)). Carbon Mapper runs two clocks, "quick-look CH4 detection products available for direct notification to operators and regulators within 72 hours" and public release "30 days after acquisition" after analysts "reject false alarms, correct or remove questionable emission estimates, and add attribution meta-data" ([Carbon Mapper Product Guide](https://assets.carbonmapper.org/documents/Carbon%20Mapper%20Product%20Guide%20-%20Data%20Definition%20&%20Specification%20v1_1_3.pdf)). The US EPA goes further and posts super-emitter notifications "excluding owner/operator attribution" ([SLB summary](https://www.slb.com/resource-library/article/2025/how-the-epas-methane-rules-are-pushing-for-transparency-and-accountability-in-2025-and-beyond)). The standard rebuttal is technical, not legal: when Kayrros reported the Karaturun East blowout, the operator said the images "likely [showed] hot vapor clouds with minimal traces of the greenhouse gas", and Kayrros held its ground because it was "extremely unlikely to mistake water vapor for methane on multiple images captured by two hyperspectral satellites" ([Eurasianet](https://eurasianet.org/kazakhstan-gives-methane-super-emitter-780000-slap-on-wrist)). Multi-sensor, multi-date corroboration is what survives dispute.

GFW's decade adds the confidence and expiry rules and a sober view of impact. Alerts not confirmed within six months "are removed from the database, whether because they were false positives, consistently covered by clouds, or small clearings with rapid vegetation regrowth" ([GLAD alerts explained](https://globalnaturewatch.org/blog/data-and-tools/glad-deforestation-alerts/)); RADD (Sentinel-1) achieves user's accuracy of 97.6% for alerts above 0.2 ha in the Congo Basin ([Reiche et al. 2021](https://iopscience.iop.org/article/10.1088/1748-9326/abd0a8)), while the global Hansen loss map carries "13 percent false positive rate and a 12 percent false negative rate" ([GFW](https://www.globalforestwatch.org/blog/data/how-accurate-is-accurate-enough-examining-the-glad-global-tree-cover-change-data-part-1/)), so publishing per-detector validation statistics inside the product is both GFW practice and what Daubert-style admissibility asks for ("the technique's margin of error must be known and controlled") ([PLOS One 2025](https://journals.plos.org/plosone/article?id=10.1371%2Fjournal.pone.0331683)). GFW's most trusted product, Places to Watch, is not automated: it filters alerts to primary forest and protected areas, ranks 5×5 km cells, then "GFW experts review all computer-generated places", producing "5–10 priority locations on a quarterly basis" ([WRI](https://www.wri.org/research/places-watch-identifying-high-priority-forest-disturbance-near-real-time-satellite-data)). And alerts alone change little: GLAD subscriptions "reduced the probability of deforestation by 18% in Africa … but detected no comparable effect on other continents and concluded that availability of alerts alone was insufficient" ([Nature Climate Change](https://www.nature.com/articles/s41558-021-01195-3)). Routing design matters more than detection sensitivity.

Climate TRACE and Global Fishing Watch define the naming posture. Climate TRACE publishes 352 million assets with ownership trees under CC BY 4.0, recording "each ownership link … the percentage owned … as long as they exceed a 5% threshold", with ownership "sourced and managed by Global Energy Monitor's Ownership team" and the caveat that a 5% owner is counted with the asset's full emissions ([Climate TRACE ownership](https://climatetrace.org/news/understanding-and-using-climate-trace-ownership-data-for-emitting-assets); [climate-trace-tools README](https://github.com/climatetracecoalition/climate-trace-tools/blob/main/climate_trace_tools/ownership/README.md)). Even so, a 2026 *Environmental Research Letters* paper alleged it was "underestimating vehicle carbon dioxide emissions in cities by an average of 70%", and Climate TRACE's defence was that the study used "outdated, anomalous data from a 2-month period when there was a bug present", corrected "a year ago" ([phys.org](https://phys.org/news/2026-05-climate-scientist-large-errors-global.html); [Climate TRACE response](https://climatetrace.org/news/climate-trace-nau-road-transport-emissions)): version every published number, keep old versions retrievable and stamp each with model and data versions so critics and defenders cite the same snapshot. Global Fishing Watch names vessels but never crimes: it publishes "apparent fishing" on a stable identifier, warns that "vessel identities can change when vessels change names or flag states", advocates permanent IMO numbers because "a ship's name can be repainted or its flag changed overnight", and lets authorities with jurisdiction (Mexico's environmental prosecutors, Chile's Legal Ocean Watch) make the illegality call ([GFW data caveats](https://globalfishingwatch.org/our-apis/documentation/docs/v3/general-api-doc/data-caveats); [GFW IMO brief](https://globalfishingwatch.org/brief/imo-numbers-for-fishing-vessels-why-permanent-identification-matters/)). SkyTruth's Cerulean treats "all detections … as potential oil slicks, not confirmed spills", assigns each candidate source a confidence score, and offers a human "Verified Slicks" tier ([Cerulean FAQ](https://skytruth.org/faq/cerulean-questions/); [SkyTruth Verified Slicks](https://skytruth.org/blog/verified-slicks-building-trust-at-the-intersection-of-ai-and-human-expertise)). The research found no defamation judgment arising from satellite-based naming of a company; the documented disputes are technical, and satellite evidence is now routine in Brazilian courts (STJ recognition, CNJ Recommendation 99/2021, 700+ final judgments in the Amazon Protects project by 2024) ([Columbia Climate Law Blog](https://blogs.law.columbia.edu/climatechange/2026/01/23/amazon-protects-phase-4-of-the-public-prosecutors-project-to-fight-deforestation-in-brazil/)) — but that absence reflects that every serious publisher already avoids unqualified accusations, and an OSS ledger's findings are leads for official systems rather than evidence themselves.

The ethics evidence points at who bears the risk of acting on an alert, not at false alerts. Community monitors in Peru and Brazil have been ambushed and killed; forest guard Paulo Paulino Guajajara was "shot dead during an ambush by illegal loggers" after guards "informed federal agencies of the threats, but they didn't take any action" ([NPR](https://www.npr.org/2019/11/03/775818673/illegal-loggers-kill-indigenous-forest-guard-member-in-brazil)), and a Wampis patrol was attacked after "government agencies pulled out of a scheduled joint operation without explanation" ([AP via Yahoo](https://www.yahoo.com/news/indigenous-wampis-ambushed-peru-government-191205526.html)). A precise public alert inside an Indigenous territory can expose local monitors rather than perpetrators, so geometry on community lands should be aggregated or delayed unless the community opts in as the routing target (the Rainforest Foundation US model), and the ledger must never identify natural persons; attribution stops at corporate and registered entities and public bodies, which also avoids GDPR-class exposure for an EU-hosted project.

Translated into policy, these become Earth Watch's trust contract, tiered by consequence to avoid the queue collapse one team hit at "200+ review requests per day … with reviewers starting to batch approvals just to stay above water" ([waxell](https://waxell.ai/blog/ai-agent-approval-workflows)):

| Tier | Action | Gate | Precedent |
| --- | --- | --- | --- |
| 0 | Internal dashboard cards, candidate log entries | None (auto) | GLAD "unconfirmed" |
| 1 | Publish an unattributed finding ("burn scar of X ha near Y; confirmed by SAR + NBR") | One async human reviewer sees the packet: map, numbers, both signals, narration diff, provenance | Cerulean "potential" + verified badge |
| 2 | Any text naming a company, facility operator, government body, or asserting causation | Four-eyes: two distinct humans, neither of whom triggered the run, enforced in SQL (`approver_1 != approver_2`, both `!= run.triggered_by`) | Two-person rule ([Devolutions](https://docs.devolutions.net/rdm/concepts/advanced-concepts/four-eyes-principle)); AP: every AI output reviewed by a journalist |
| 3 | Tier-2 items enter `awaiting_reply` for a fixed window (72 h private notice; 30-day public release) and cannot leave before the timer or a logged reply; reply or "no response by date" is embedded verbatim | Workflow state with timer | MARS / Carbon Mapper two clocks |

Around the tiers: confidence equals number of independent detectors, low-confidence findings are visibly provisional and expire (GLAD's six months); a minimum-area threshold (RADD's 0.2 ha; EUDR's 4 ha point-vs-polygon rule) and a driver classification (natural vs human) precede any "deforestation" label; assets and places are named with confidence, owners only via a cited registry (GEM, Climate TRACE, EUDR DDS) with the stake threshold printed; "observed" and "alleged" are separate schema fields; `false_positive` and `retracted` are events never deleted and feed a published per-detector error rate; any error in a name or place gets a dated, visible correction, Bellingcat's minimum ([Bellingcat editorial standards](https://www.bellingcat.com/about/editorial-standards-practices/)); a finding nobody reviews within its SLA expires rather than auto-publishes; and a very low-volume, human-authored "cases" layer sits on top of the raw feed, as Places to Watch and MAAP reports do. Findings data is CC BY 4.0 (Climate TRACE's choice, maximising reuse by regulators and journalists); non-commercial licences shrink downstream use and are not open by the OKF definition.

EU law now shapes the disclosure block. AI Act Article 50 applies from 2 August 2026 to all in-scope systems, with fines "up to €15 million or 3% of worldwide annual turnover" ([Cooley](https://www.cooley.com/news/insight/2026/2026-08-03-eu-ai-act-transparency-obligations-take-effect-2-august-2026)); the digital-omnibus deal moves the Article 50(2) watermarking deadline to 2 December 2026 ([Usercentrics](https://usercentrics.com/knowledge-hub/eu-ai-act-high-risk-delay-article-50-transparency-consent/)). AI-generated text published to inform the public escapes machine-readable marking only under Article 50(4)'s human-review exemption, which the Commission's July 2026 guidelines read narrowly: review "must involve 'deliberate examination of the substance of the content' by persons with 'relevant competence and professional judgement'", requiring "a documented editorial workflow with identified responsible persons … who reviewed it, what they could change, who approved publication" ([Global Policy Watch](https://www.globalpolicywatch.com/2026/05/10-takeaways-european-commission-draft-guidelines-on-ai-transparency-under-the-eu-ai-act/); [Bird & Bird](https://www.twobirds.com/en/insights/2026/european-commission-adopts-final-guidelines-on-ai-act-article-50-transparency-obligations-first-impr)). The review queue's journaled who/when/diff produces that evidence for free; the site should nonetheless also emit a machine-readable "AI-assisted" marker (schema.org JSON-LD with the attestation link) so 50(2)-style marking holds even if the exemption is contested, plus an AP-style plain-language line ("Drafted by an AI system from satellite data; reviewed and approved by <name>, <date>"), matching AP's July 2026 rule that "every AI-generated output must be reviewed and edited by an AP journalist before anything reaches readers" ([AP standards](https://www.newspapers.org/stories/ap-updates-newsroom-standards-for-artificial-intelligence,4167054)). A public system card (rules, thresholds, model ids, eval scores, known failure modes, last drift check) should be versioned and linked from every finding. For provenance standards, the in-toto/DSSE attestation is the security root; the `openfab/generation` predicate proposed to OpenSSF in June 2026 (model id, prompt SHA-256 fingerprint, acceptance checks, N-of-M human sign-offs) is the right model for an `earthdeck/finding-provenance/v1` predicate ([ossf/tac #628](https://github.com/ossf/tac/issues/628)); C2PA manifests belong only on rendered images as a display-layer credential, because an independent 2026 analysis concluded the current specifications "should not yet be relied upon for high-stakes uses such as financial disclosures, journalism, or legal evidence" ([arXiv 2604.24890](https://arxiv.org/html/2604.24890v1)), and no satellite operator was found shipping C2PA on imagery.

## US federal data is the durability risk; EU and UN sources anchor the source table

The ten-year lens inverts the usual ranking. Copernicus is "free, full and open" with explicit permission to reproduce, distribute and adapt under a "Contains modified Copernicus Sentinel data [Year]" attribution ([Sentinel Data Legal Notice](https://sentinels.copernicus.eu/documents/247904/690755/Sentinel_Data_Legal_Notice)); ESA is moving Sentinel-1/2/3 to Zarr as the native format through EOPF, with GeoZarr targeting OGC review in 2026 ([zarr.eopf.copernicus.eu](https://zarr.eopf.copernicus.eu/); [geozarr.org](https://geozarr.org/faq)); and CDSE launched a STAC catalogue at `stac.dataspace.copernicus.eu/v1` in Feb 2025 and added nine Sentinel-5P L2 collections including CH4 to openEO on 17 Sep 2026 ([CDSE news 2025-02-13](https://dataspace.copernicus.eu/news/2025-2-13-release-new-cdse-stac-catalogue); [CDSE news 2026-09-17](https://dataspace.copernicus.eu/news/2026-9-17-new-sentinel-5p-level-2-collections-available-openeo-cdse)). Meanwhile NOAA decommissioned dozens of products in 2025 (NCEI snow and ice, DMSP permanently, Billion-Dollar Disasters) and will end all remaining Suomi-NPP science products on or after 1 Nov 2026 ([NESDIS 2025 Notice of Changes](https://www.nesdis.noaa.gov/about/documents-reports/notice-of-changes/2025-notice-of-changes); [Eos](https://eos.org/research-and-developments/noaa-datasets-will-soon-disappear)); NSIDC's Sea Ice Index moved to "Basic" service "due to funding limitations" and now runs on JAXA AMSR2 from 1 Jan 2025 ([Sea Ice Index v4](https://nsidc.org/data/g02135/versions/4)); the FY2026 proposal cut NASA Earth Science by $1.161 B ([Project Geospatial](https://projectgeospatial.org/geospatial-frontiers/nation-at-a-crossroads-fy2026-budget-proposal-threatens-to-dismantle-u-s-geospatial-supremacy-risking-economic-and-infrastructural-integrity)); and GFW itself reported that "as of October 2025, some of the data underlying Global Forest Watch is no longer being updated due to U.S. federal funding disruptions" after USAID cancelled 83% of its programs ([Wikipedia: GFW](https://en.wikipedia.org/wiki/Global_Forest_Watch)). Even the Mauna Loa CO₂ record was targeted in the FY2027 budget, though NOAA says it is secure ([Forbes](https://www.forbes.com/sites/we-dont-have-time/2026/05/30/mauna-loa-observatory-survives-lava-budget-cuts-and-politics/)). MethaneSAT, the philanthropic single-satellite bet, was lost on 20 June 2025 after ~400 contact attempts ([EDF](https://www.edf.org/media/methanesat-loses-contact-satellite)), and Planet's NICFI tropical basemaps ended in Jan 2025 with the next phase cancelled ([Collect Earth](https://www.collect.earth/planet-imagery-via-nicfi-is-no-longer-available-on-ceo/)). The engineering rules that follow: every upstream URL lives in config with a documented substitute (S-NPP → NOAA-20/21; `ghoapi` → WHO hub; Climate TRACE `/v7` → `/vN`); every ingested series is snapshotted to the project's own storage with source and licence metadata so a decommission does not blank the ledger; EU mirrors are preferred where they exist; and the UI displays upstream liveness and flags stale detectors. For discovery, query Earth Search (Element 84 has "taken over the Sentinel ingestion pipeline on AWS" for long-term stability) and CDSE STAC redundantly, with the Planetary Computer as a third source for non-Sentinel collections, since its data catalog and STAC API remain live even though the Hub retired in June 2024 and enterprise work moved to "Pro" ([FOSS4G 2025](https://talks.osgeo.org/foss4g-2025/talk/DZRYCJ/); [microsoft/PlanetaryComputer #347](https://github.com/microsoft/PlanetaryComputer/discussions/347)).

Licences constrain the ledger more than availability does. The World Database on Protected Areas cannot be redistributed: to provide a service where WDPA data are downloadable you "must contact protectedareas@unep-wcmc.org for permission" and online publication "must not be downloadable" ([UNEP-WCMC WDPA licence](https://www.unep-wcmc.org/en/wdpa-data-license)), so the ledger stores `WDPA_ID`, name, designation and computed intersection statistics and deep-links to Protected Planet, while OSM `boundary=protected_area` (ODbL) and LandMark (CC BY) are the republishable fallbacks, with OSM-derived rows kept in a separate "collective" table per the OSMF guideline so the ledger's own records are not relicensed ([OSMF Collective Database Guideline](https://osmfoundation.org/wiki/License/Community_Guidelines/Collective_Database_Guideline_Guideline)). VIIRS Nightfire has required a free account plus a signed Data Use License since 10 Jan 2025; nightly detections cannot be republished raw, but "monthly and annual temporal aggregations may be redistributed without restriction" with credit ([VNF license PDF](https://eogdata.mines.edu/files/vnf_license_agreement_form.pdf)), so the flaring wedge must be built on per-asset monthly aggregates plus public-domain FIRMS night-time high-FRP detections joined to known assets. Carbon Mapper's licence is non-commercial, ShareAlike, "non-sublicensable, revocable", and reserves the right to change APIs with "no commitment to maintain any specific functionality or data availability" ([Carbon Mapper Terms](https://carbonmapper.org/terms)): link to plume pages by id, cache only derived counts. EDGAR's IEA-derived CO₂ component is CC BY-NC-ND while its CH4/N2O/F-gas grids are CC BY 4.0 ([EDGAR](https://edgar.jrc.ec.europa.eu/edgar_smod)); IPC is CC BY-NC-SA 3.0 IGO; ACLED moved to gated OAuth in 2025; Freedom House needs permission for commercial use; V-Dem's CC BY-SA propagates share-alike into derived tables.

Two quota realities shape the sweep design. At the safe planning number of 10,000 CDSE processing units per month, Sentinel Hub covers a few thousand small 512-px three-band requests — enough for a few hundred AOIs weekly, not thousands daily — so planet-scale optical work should read Sentinel-2 COGs directly from Earth Search (zero PUs, HTTP range reads via geotiff.js) and reserve Sentinel Hub/openEO for SAR and S5P, where server-side processing substitutes for a Python stack ([CDSE PU calculator](https://dataspace.copernicus.eu/cases/sentinel-hub-pu-calculator-demystifying-your-costs)). And FIRMS' 5,000 transactions per 10 minutes is generous only if a sweep makes one large-bbox, one-day pull per run and joins to AOIs locally in DuckDB rather than one call per AOI ([FIRMS map key](https://firms.modaps.eosdis.nasa.gov/api/map_key/)). Cache at three layers: raw HTTP responses content-addressed on object storage with a per-source TTL, per-AOI derived observations in the ledger, and STAC search results per AOI/day in stac-geoparquet, so re-runs and backfills never depend on a remote API being up.

## The site is static files on a CDN; the Node dashboard stays local mission control

Publishing follows the same static-first logic as the ledger. PMTiles is a single-file tile archive read by HTTP range requests, so "maps run directly from S3/R2 with no tile server", with MapLibre, Leaflet and OpenLayers plugins, a BSD-3 implementation and a public-domain spec ([protomaps/PMTiles](https://github.com/protomaps/PMTiles/blob/main/README.md)); DuckDB-WASM in the browser reads the same GeoParquet partitions that machine consumers read with `read_parquet('https://…/findings/year=*/…')`, so there is no API server at all. The proposed feed layout is `feeds/latest.geojson` (last N published findings), `feeds/aoi/<id>/history.parquet` with a `.csv` mirror, `feeds/findings/year=YYYY/month=MM/*.parquet`, `catalog/items.parquet` (stac-geoparquet of evidence chips), `tiles/aoi.pmtiles` and `tiles/findings.pmtiles`, `ledger/` (tiles, entries, checkpoint, `.ots` proofs, `keys.json`), and an `index.json` manifest with content hashes and generation time; each scheduled run appends one Parquet partition, rewrites only the small `latest.*` and affected AOI files, and fully regenerates PMTiles with tippecanoe, which is simpler than incremental tiling. Machine consumers get exactly what leverage-holders and journalists need — the same ledger filtered by asset, commodity or country — plus an Atom/JSON feed per AOI and, following Global Fishing Watch's official R and Python clients ([gfwr](https://github.com/GlobalFishingWatch/gfwr)), a small TS/Python client and the MCP server itself as the "API"; this is how downstream adoption compounds.

Hosting should be Cloudflare R2 for data (10 GB storage and 1M operations per month free, no egress fees, Range and CORS supported) with Cloudflare Pages or GitHub Pages for the SPA shell ([Cloudflare pricing](https://developers.cloudflare.com/workers/platform/pricing/)). GitHub Pages is the wrong shape for PMTiles and Parquet at scale: soft size and bandwidth caps and no control over Range, CORS or caching headers (exact limits could not be fetched; verify at the GitHub Pages limits page). Source Cooperative, which positions itself as "the data publishing utility for the web" and hosts over a petabyte on grant funding, is the candidate second home once its intake process for small publishers is confirmed ([source.coop](https://source.coop/radiantearth)). The Vite/MapLibre web UI becomes the public site's static build, gaining a Watch tab (cases list, case page with map, evidence, timeline and status, verification widget), the world pulse grid, the review queue (served locally by the dashboard, never on the public site), sweep-health tiles and a provenance viewer. The Node `http` dashboard server keeps its role as the live local surface — SSE cards, `/review`, `/api/state` — and subscribes to the published `feeds/latest.geojson` so local and public views share one data contract; it never becomes the public origin. The basemap stays NASA GIBS with a configured fallback, since GIBS is a US federal service. Governance follows the long-lived exemplars: OSMF's seven-member elected board that is "supporting, but not controlling" the project ([Wikipedia: OSMF](https://en.wikipedia.org/wiki/OpenStreetMap_Foundation)), an explicit published shutdown and archival plan (yearly consolidated Parquet snapshot plus checksums mirrored across R2, Source Cooperative and the Internet Archive, and datasets on Zenodo or Hugging Face as UNEP does for MARS-S2L), MIT/Apache code, CC BY 4.0 findings, and, if funds ever exist, a Wikimedia-style 4% spending rule for a reserve ([Endowment spending policy](https://foundation.wikimedia.org/wiki/Endowment:Wikimedia_Endowment_Spending_Policy)).

The world pulse is the one component with no engagement evidence behind it, and the report should say so. One large study finds negative headline words raise click-through ([Nature Human Behaviour 2023](https://www.nature.com/articles/s41562-023-01538-4)), a 2025 six-country study finds negative posts get *less* engagement ([arXiv 2507.19300](https://arxiv.org/html/2507.19300v1)), and no study tests whether good-news content in an accountability dashboard changes trust. The defensible rationale is therefore accountability completeness — the ledger must show closure states honestly — with MARS's published "25 mitigation cases" and 100%-response countries as the precedent for reporting good news as response data. Build `world_pulse` on OWID's slug-based CSV URLs with companion `.metadata.json` carrying source and licence per indicator (`csvType=filtered&country=…&time=…` keeps payloads small), plus World Bank v2 (`mrv=N`), UN SDG, UNHCR and UCDP, reusing `src/series.ts` and a one-line-per-indicator registry with `betterWhen` ([OWID chart API](https://docs.owid.io/projects/etl/api/chart-api/); [WB API](https://datahelpdesk.worldbank.org/knowledgebase/articles/898581-api-basic-call-structures)). Check each OWID indicator's upstream licence before republishing (Freedom House and IEA-derived charts are restricted), snapshot every series, and show data-liveness per indicator.

## Nothing written in v1 is thrown away: the v1 → v2 → v3 ladder

The ladder is designed so only the scheduler, the query tier and the witness quorum change with scale; every file format is an open Apache, OGC, IETF or C2SP standard, and the ledger written in year one is the ledger read in year ten.

**v1 — "the repo is the platform" (weeks; $0–5/month).** Ledger: `ledger/entries.jsonl` (one DSSE envelope per line, JCS payload, in-toto Statement, UUIDv7 ids), an in-house RFC 6962/tlog-tiles writer producing `tile/…` and an Ed25519 signed-note `checkpoint` (origin `earthdeck.dev/findings/v1`), keyless Sigstore signature of each checkpoint from the Actions OIDC identity uploaded to Rekor v2, `sha256(checkpoint)` submitted to OpenTimestamps with the `.ots` stored alongside, a published `verify.ts` and spec doc, and at least two mirrors (GitHub plus R2 or an IPFS pin). Kernel: `packages/watch/` with SQLite or file journal, three rules with second-signal requirements (forest loss via GFW alert + NDVI drop; fires in protected areas via FIRMS cluster + NBR; methane anomaly via S5P Statistical API + Climate TRACE asset), watermark-driven idempotent sweeps, `finding_key` UNIQUE, Claude Code headless as the first `LlmStep` with Ajv post-validation and the numeric-faithfulness check, a single-reviewer queue served by the dashboard, heartbeat and external watchdog, `total_cost_usd` budget cap, plain "AI-drafted, human-reviewed" disclosure. ## Where the 2026-09-26 plan should change

The plan's strategic decisions survive intact — option B (extend the dashboard, static export, in-repo ledger), the methane/flaring then deforestation/EUDR wedges, "the deterministic layer decides what counts as a finding", assets and institutions never people, human sign-off before naming, `false_positive` rows never deleted, contributor-editable watchlists and detectors. The research changes the mechanisms in seven places. First, the ledger: replace `prevHash → hash` rows with event-sourced in-toto/DSSE statements in a tlog-tiles Merkle log with signed checkpoints and Rekor v2 + OpenTimestamps anchors; the JSONL file stays (one envelope per line) but is no longer the trust root, and `ledger_update(id, status, note)` becomes an append of a `status_changed` event, never an update. Second, the status machine gains states the plan lacks: `awaiting_confirmation` with a deadline and expiry (GLAD's six months), `awaiting_reply` with a timer, `needs_second_approval` for Tier 2, `retracted`, and `expired`; and Tier-2 naming requires two reviewers rather than one `review.by`. Third, scheduling: "every 6 h" becomes watermark-driven catch-up in a dedicated workflow with keepalive, `concurrency`, `workflow_dispatch` and an external watchdog, because Actions cron was hours late or skipped in 2026 and auto-disables after 60 idle days. Fourth, storage and publishing: the JSONL ledger is mirrored into GeoParquet partitions on R2 with PMTiles and DuckDB-WASM, and the `watch-data` branch plus GitHub Pages carries only the site shell and small feeds, not tiles or Parquet. Fifth, the analyst: `src/watch/analyst.ts` should not be the thing that "writes back as `verified` when the 2nd signal agrees" — the deterministic confirmation step does that; the analyst narrates confirmed findings under a hard schema with `evidence_refs[]`, is post-validated by Ajv and the numeric-faithfulness check, and sits behind the `LlmStep` interface so Claude Code headless is one adapter among several. Sixth, data sources: the `flaring` tool must publish only monthly/annual VNF aggregates (nightly detections are not redistributable) and should drop `VIIRS_SNPP_NRT` before 1 Nov 2026; `protected_areas` must never serve WDPA geometry, only IDs and intersection stats, with OSM/LandMark as the republishable layer; `methane_plumes` should add EMIT plume GeoJSON and UNEP MARS as republishable point-source feeds alongside S5P; `emitters` should pin Climate TRACE `/v7` in config and ingest GEM ownership spreadsheets as versioned static files; and `world_pulse` should check each OWID indicator's upstream licence. Seventh, compliance and disclosure: the review journal should be designed from day one to produce the Article 50(4) evidence (who reviewed, what they could change, who approved), every published finding should carry the machine-readable AI-assisted marker and plain-language disclosure line, and `TRUST.md` should adopt the two-clock timing rule (72 h private, 30-day public with reply embedded verbatim), the corrections rule for names and places, and the Indigenous-lands aggregation rule.

## Conclusion

The deepest lesson across all five research threads is that durability comes from choosing standards whose survival does not depend on any single organisation surviving — RFC 6962 hashing, C2SP tiles, Parquet's native geometry, STAC and OGC Records, PMTiles, RFC 9562 identifiers — and then arranging the system so that servers, schedulers, LLM vendors and even the project's own Node code are all replaceable around a static, self-describing corpus of files. That same principle governs data sourcing: the 2025–2026 shocks to NOAA, NASA, NSIDC, GFW and MethaneSAT show that the open-data landscape is less stable than the open-standards landscape, so the ledger must snapshot its inputs and display upstream liveness as carefully as it proves its own integrity.

The second lesson is that the accountability loop's hard part is social, not technical. MARS's 12% response rate with UN backing, GFW's 18%-in-Africa-only effect, and the deaths of community monitors who acted on alerts mean Earth Watch's value will be decided by routing to actors with legal duties, by publishing replies and non-replies honestly, by protecting the people nearest the finding, and by the discipline of never letting the model decide what is true or who is responsible. Earth Watch would be early — the research found no fully unattended public-publishing EO agent anywhere — which is precisely why the conservative gates, the public system card and the published error rate are not overhead but the product.
